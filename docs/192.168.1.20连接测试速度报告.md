## 5. 延迟构成分析（2026-11-03 20:52–20:57 补测）

疑问：全在局域网，ping 192.168.1.20 才 1ms，为什么 RPC 要 75~205ms？

### 5.1 逐段实测

| 分段 | 耗时 | 测量方式 |
|---|---|---|
| 本机签名（PEM 解析+ECDSA sign） | ~2–4 ms | 本地微基准：解析 0.2ms、sign avg 2.2ms（NIST256p 纯 Python ecdsa） |
| broker 管线（本机↔192.168.1.20↔本机 自回环，无签名无手机） | avg 4.7 ms（2.2–9.5） | manager 自回环 10 次 |
| ping 192.168.1.20（broker） | 1 ms | 用户实测 |
| **ping 手机 192.168.1.109（ICMP，内核层）** | **min 3 / avg 74 / max 144 ms** | 20 次 ping，抖动极大 |
| 手机端 ECDSA 验签 verify | 16–22 ms | RPC 就地计时（手机 CPU 内部计时，不受无线抖动污染） |
| 手机端签名 sign（回包不签名，仅备用能力） | ~6 ms | 同上 |
| 手机端代码执行+回包组包 | **~0.4 ms** | RPC 内嵌时间戳分解（server_time − 代码入口时间） |
| 其余（手机 Python 线程调度/队列唤醒/JSON/去重 + 本机收包分发） | ~10–30 ms | 残差 |

### 5.2 结论：延迟出现在手机的 Wi-Fi 射频，不是 broker、不是软件栈

- ICMP 是内核处理、不经应用——ping 手机本身就 3~144ms（平均 74ms），
  而 ping broker 只要 1ms。**瓶颈是手机→AP 这一跳无线**。
- 典型特征吻合 Wi-Fi 省电（PSM/DTIM）：手机锁屏休眠时射频周期性休眠，
  下行包要等下一个信标窗口，表现为"快慢交替"（3ms 和 144ms 交替出现）。
- **背靠背突发实验佐证**：8 个无间隔 RPC 连发为 41/66/96 ms
  （min/avg/max），而间隔 ≥0.3s 的 10 个样本是 78/125/205 ms。
  流量把射频保持在唤醒窗口内，延迟即大幅收敛。
- 软件栈合计只占 ~30–45ms（验签 18ms + 调度/队列 + 签名 2ms + 管线 5ms，
  执行本身 0.4ms 可忽略）。
- 附带发现：手机时钟比本机快约 1.2s（分解测量时钟偏移 ≈ +1208ms），
  在重放窗口内可正常工作，但建议 NTP 对时，避免窗口收紧后被拒收。

### 5.3 降延迟建议

1. 测试/高频 RPC 时让手机保持亮屏或"充电时 WLAN 不休眠"（开发者选项），
   或 `adb shell svc power stayon true`（本机 PATH 无 adb；应用内 `input
   keyevent` 无系统权限，唤醒失败 r=65280）。
2. 需要持续低延迟时给手机插电/常亮；锁屏闲置时 100ms 级延迟属射频物理特性。
3. 验签 16–22ms 若在意，可换原生 crypto 实现（如 cryptography/OpenSSL），
   纯 Python ecdsa 在手机上是软件侧最大单项。
